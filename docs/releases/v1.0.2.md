# v1.0.2 — Egress Tunnel Fix

> **Promotion of `v1.0.2-rc1`.** This is a pure version-metadata promotion: the
> code at the `1.0.2-rc1` anchor and at this tag is byte-identical apart from
> the version carriers. `scripts/release/classify_diff.py` therefore returns
> `release_metadata_only=true` / verdict `INHERITED`, and the certification
> earned at the RC anchor carries forward.

**What changes versus v1.0.1:** one defect fix, plus the regression tests that
keep it fixed. Nothing else.

## Fixed: egress proxy CONNECT tunnel corruption

**This is the defect disclosed as the first known limitation of the v1.0.1
release notes.** It was present identically in v1.0.0 and v1.0.1 and was not a
v1.0.1 regression; it is fixed here for the first time.

The proxy's CONNECT handler consumed **only the request line**. The rest of the
request — `Host:`, `Proxy-Connection:`, and the terminating blank line —
remained in the `StreamReader` buffer and was piped to the upstream as if it
were tunnel payload, corrupting the tunneled protocol:

- TLS through the proxy failed with `SSL: WRONG_VERSION_NUMBER`, because the
  origin received a stray `Host:` line instead of the ClientHello.
- Plain-HTTP origins answered `400 ... malformed HTTP request "Host: ..."`.

**Impact:** every real network acquisition routed through the egress proxy
returned zero bytes, so acquisition runs terminated `BLOCKED`. Layer-1 SSRF
validation, the production admission gates, and readiness/claim behaviour were
never affected — which is why the defect survived every automated gate: no
suite performed a byte-level fetch through the proxy.

**Fix:** consume the remainder of the CONNECT request headers, line by line up
to the blank line, before establishing the tunnel. (Not
`readuntil(b"\r\n\r\n")`: the request line's own CRLF has already been
consumed, so a headers-less CONNECT would leave only `\r\n` in the buffer and
a four-byte terminator search would stall — and then swallow the client's TLS
ClientHello as if it were headers.)

A client that never sends the terminating blank line is malformed; it is waited
out for one short timeout (5s) and then tunneled anyway, so non-conformant
clients are slowed, not broken.

### Why CI missed it, and what now prevents that

Every certification suite verified deployment, migration, readiness and schema
invariants — never a byte fetched through the proxy. Two guards now exist:

- `tests/test_phase_28_5_egress_proxy.py` drives a raw CONNECT client against a
  local upstream and asserts the upstream body arrives intact.
- `tests/test_phase_28_5_egress_proxy.py::test_connect_tunnel_fetches_real_https_body`
  (marker `network`) fetches real public HTTPS origins through the proxy and
  asserts a body comes back. It runs in the `ci.yml` suite — the same suite the
  release chain's `quality-gates` job runs — so a regression now fails the
  release before publication. Targets are pre-flighted with a direct fetch so
  runners without egress skip rather than fail, and the proxy's own policy
  denials (403/407) are distinguished from transport failures, since only the
  latter indicate a broken tunnel.

Verified in both directions: on the pre-fix code these tests fail (the tunnel
yields no body); on the fixed code they pass, and a real HTTPS fetch through
the proxy returns the origin's body.

## Known limitations

Carried forward from v1.0.1; **the egress CONNECT defect is no longer among
them**:

- **Response EDR/WAF/Firewall providers remain mock-only.** No production
  device integration exists in the tree; enabling one is not a configuration
  option. The approval, evidence, audit and rollback framework around them is
  real and certified.
- **Zeek TSV is unsupported.** JSONL is the only supported ingest format; TSV
  input is rejected with an actionable error.
- **24-hour soak not executed.** The certified soak for this line ran for
  2 hours. The 24-hour endurance run remains outstanding.
- **SLOs remain candidates.** The SLO values are derived from measured data as
  candidates; promotion to enforced SLOs is a product decision after a full
  month of production data.

## Upgrade

See [`docs/deployment/upgrade.md`](../deployment/upgrade.md). Upgrading from
v1.0.1 is a standard patch upgrade — no breaking operational change, no
migration surprise. Deployments that worked around the egress defect by
disabling the proxy can re-enable it after upgrading.
